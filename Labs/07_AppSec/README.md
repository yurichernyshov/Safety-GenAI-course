Теоретические сведения

Уязвимости, связанные с программным кодом приложений, становятся все более частыми. 
Для этого есть несколько причин: часто используемые библиотеки open-source, применение систем автоматической генерации кода (в т.ч. LLM), сложные схемы supply-chain в создании информационных систем (с привлечением цепочки субподрядчиков) и другие. Поэтому актуальной становится профессия AppSec специалиста, который отвечает за безопасность разработки.
Важным инструментом AppSec является SAST (Static Application Security Testing), включающий процедуры и программное обеспечение для статического анализа безопасности приложений. SAST проверяет исходный код без его выполнения, до компиляции, при этом анализирует исходный код, байт-код. Также существуют инструменты DAST (Dynamic Application Security Testing), которые применяются после окончания этапа написания кода и, кроме самого кода, используют результат компиляции кода анализируя динамическое поведение программы.
Преимущества SAST: раннее обнаружение уязвимостей, полный охват кода, возможность более быстрой и дешевой митигации (устранения) уязвимостей. Недостатки SAST: ложные срабатывания (false positive), отсутствие возможности обнаружить runtime-проблему.
Semgrep — легкий статический анализатор кода с поддержкой кастомных правил.

Ключевые особенности:
- Поддержка 30+ языков (Python, JavaScript, Java, Go, etc.)
- Простой синтаксис правил (pattern-based)
- Быстрое сканирование
- Интеграция с CI/CD (GitHub Actions, GitLab CI, Jenkins)

Пример структуры правила Semgrep:
```json
rules:
  - id: rule-identifier
    pattern: $FUNC(..., $PASSWORD, ...)
    message: "Уязвимость: передача пароля в функцию"
    severity: ERROR
    languages: [python]
```

Существуют различные типы уязвимостей в программном коде, в зависимости от языка программирования. Например, в языке С/C++, который поддерживает прямую работу с памятью с помощью функций malloc и т.п., актуальными являются уязвимости типа «переполнение буфера», когда программа имеет возможность читать или записывать информацию по адресам, находящимся за пределами разрешенной для этого памяти. 
Это дает возможность украсть информацию, либо записать вредоносную информацию и даже исполнить вредоносный код. 
В языках более высокого уровня, в которых работа с памятью выполняется системой (java, python и т.п.) подобных уязвимостей уже нет, однако могут быть другие, связанные с особенностями реализуемых приложений. 
Например, для приложений, работающих с web и базами данных, актуальными являются уязвимости «SQL инъекция» или «Инъекция команды операционной системы».
Для web приложений существует сообщество OWASP, которое занимается систематизацией, описанием и разработкой мер обнаружения и устранения уязвимостей, связанных с web. Однако в последнее время функции этой организации расширились, и эксперты OWASP занимаются анализом других функций и технологий, в том числе LLM и агентов искусственного интеллекта.

Примеры уязвимостей по OWASP Top 10
|Уязвимость|Описание|Пример|
|:-:|:-:|:-:|
|SQL Injection|Внедрение SQL кода|f”SELECT * FROM users WHERE id={user_id}”|
|Command Injection|Выполнение системных команд|os.system(f“ping {host}”)|
|Hardcoded Secrets|Секретная информация, оставленная в программном коде|API_KEY=”12345”|
|Insecure Deserialization|Небезопасная десериализация|pickle.load(model)|
|Weak Cryptography|Слабости криптографических алгоритмов|hashlib.md5(password)|

Безопасность ML приложений

MLSecOps/LLMSecOps фокусируется на специфических уязвимостях, связанных с машинным обучением (ML) и большими языковыми моделями (LLM).

Безопасность ML-систем (MLSecOps) имеет уникальные отличия от традиционной разработки. Но и много общего

Примеры:
В ML чаще работа с неструктурированными данными (изображения, тексты), которые сложно валидировать (например, с помощью регулярных выражений).

Появляются уязвимости нового типа, однако очень похожие на «классические»: Promt инъекция (похожа на SQL инъекцию), Indirect Prompting (схожие черты с хранимой XSS), отравление данных (злонамеренные компоненты ПО, бэкдоры), model inversion (схожие черты с реверс-инжинирингом исполняемого кода)
Существенно расширен перечень объектов, подверженных уязвимостям. Кроме кода, файлов конфигурации и скриптов для автоматизации в проектах ML: наборы данных (датасеты) и правила их обработки, веса моделей, конвейеры обучения.
Есть своя стандарттизация (OWASP Top 10 LLM и т.п.)

Ключевые риски (MITRE ATLAS & OWASP LLM Top 10):
•	LLM01: Prompt Injection — внедрение вредоносных инструкций в промпт.
•	LLM02: Insecure Output Handling — выполнение кода, сгенерированного моделью.
•	ML01: Insecure Model Loading — загрузка непроверенных весов модели (pickle/torch).
•	ML02: Data Poisoning — компрометация обучающих данных.
•	Secrets Management — утечка API-ключей провайдеров LLM.

Реализуйте простой фильтр ввода для LLM-агента:
def detect_injection(text):
    forbidden_phrases = ["ignore previous instructions", "system prompt", "developer mode"]
    return any(phrase in text.lower() for phrase in forbidden_phrases)
